# Verbatim Harbor v0.1：运行、容量与恢复

本文件描述当前 v0.1 的运行边界。`README.exact32.md` 与 `PROVENANCE.md` 内的上游历史说明不作为当前参赛状态或容量承诺。

## 资源与容量声明

生产服务使用单个 Uvicorn worker、SQLite 和远程 Embedding。接口 top_k 上限为 100，证据预算为 24000 字符；用户索引缓存默认最多 4 个用户，缓存数量不是每用户数据量上限。

索引按用户装入内存，长文档、大用户及并发请求可能增加内存和延迟。Embedding 限流、配额和网络同样影响吞吐。

本仓库记录的原 Full 请求参数为 `max_add_concurrency=16`、`search_concurrency=16`、`top_k=100`，这是当时的编排设置，不是已验证的稳定容量或推荐并发。合成检查和 Smoke 不能证明 Full 规模性能。内存限制与上游限流可能引发查询超时，不能据上述参数作吞吐保证。

百炼适配器默认单次尝试超时 60 秒、最多 3 次，有界退避；这不是整个 Add/Search 请求的总时限。现行 API Guide 的单次请求最长 30 分钟。代理、供应商调用与平台截止需协同核验，不通过无限加长超时掩盖阻塞。不得在 Full 中擅自修改并发、缓存、内存限额或模型配置。

## 数据、命名空间和重试

- 持久化库包含来源、片段/向量、用户修订号和 `(user_id, request_id)` 幂等状态，恢复时一并保留。
- 用户隔离依据 user_id，同用户跨 session 检索；不为清理缓存清空数据或重建命名空间。
- Add 持久化后才返回 200；重试使用相同 ID、载荷与消息顺序，409 冲突需排查，不能换 ID 重复写入。
- 活跃 SQLite 的主库及 WAL/SHM 应按一致性备份流程处理，不能随意删除辅助文件或只复制未 checkpoint 的主库。备份含评测数据，仅放在获授权的私密位置。

## Full 异常处理

核对任务 ID、阶段、错误摘要、时间与内部日志。记录必要状态码、时延、身份摘要与资源指标，不公开用户正文、密钥或评测数据。

保留原参评源码、依赖、模型、关键配置、数据库、命名空间和幂等记录。`retryable=true` 不等于允许自行改变实现或清库。需要改变参评实现、资源配置或无法确认原数据可恢复时，先联系 AML 团队，取得对原任务恢复点及处理方式的确认。不自行创建新 Full 代替故障续跑。

Commit、归档哈希和幂等摘要用于审计，不替代数据库完整性检查，也不证明任务完成。服务端记录和平台结果的对应关系须经复核。

## 数据留存

评测数据及派生副本仅用于当前任务，不用于训练、微调、产品分析、数据集重建或对外传播，不提交至仓库。依现行规则，任务完成后 30 天内删除相关数据；延期须事先获得主办方书面同意。故障恢复按主办方要求保留，删除与恢复均不在本文档补充时执行。
